# 0003. 앞 단계가 실패해도 뒤 단계는 DB에 있는 것으로 계속 돈다

- 상태: 채택
- 날짜: 2026-10-02
- 근거 기록: `HISTORY.md` 2026-10-02 「관련성 판정 기준을 좁힌 뒤 재판정」

## 배경

2026-10-02 `pnpm pipeline:collect`가 arXiv 첫 요청에서 `429`로 죽었다. DB에는 이미 수집·임베딩된 논문과
후보가 있었고, 매칭·관련성 판정에는 arXiv가 필요 없었다. 그런데 `main()`이 수집 → 임베딩 → 매칭을 한
줄로 이어 부르고 있어서 **수집 실패가 판정까지 막았다.** 판정은 `match()`만 따로 실행해서 돌렸다.

같은 구조가 한 층 위에도 있다. `pipeline:run`은 `collect && evaluate && brief`라서 collect가 exit 1이면
그날 evaluate와 brief도 돌지 않는다. 외부 API 하나의 일시 장애가 그날 브리핑 전체를 지운다.

CLAUDE.md는 "한 단계가 실패해도 이전 단계 결과가 남아 재시도할 수 있어야 한다"고 한다. 결과는 남았지만,
**그 결과로 할 수 있는 뒤 단계까지 멈추는 것**은 이 원칙이 말하지 않은 구멍이었다. 사용자는 arXiv 상태와
상관없이 어제까지 쌓인 것으로 만든 브리핑을 받아야 한다.

## 검토한 선택지

### A. 단계마다 격리 — 실패는 기록하고 다음 단계를 계속, 끝에 exit 1

- 수집이 죽어도 임베딩·매칭은 DB에 있는 것으로 돈다. 임베딩이 죽어도(Voyage 장애) 이미 임베딩된 논문으로 매칭한다.
- 실패는 모아 두었다가 모든 단계가 끝난 뒤 한 번에 던진다. cron은 여전히 exit 1을 보고 알람이 울린다.
- 대가: exit 1인데 브리핑은 나간다. "실패"의 의미가 "아무것도 안 됨"에서 "어딘가 실패함"으로 바뀐다 —
  로그의 단계별 요약으로 무엇이 실패했는지 봐야 한다.

### B. 수집 실패를 경고로 낮추고 exit 0

- 브리핑은 나가지만, 매일 429가 나도 cron은 초록불이다. 수집이 며칠째 멈춘 것을 아무도 모른다.
  임베딩 전량 실패를 exit 1로 바꾼 이유(조용한 실패 금지)와 정면으로 어긋난다.

### C. 단계를 별도 프로세스로 쪼개 스케줄러가 각각 돌린다

- 격리는 가장 확실하지만, 지금은 배치 실행 방식(Vercel Cron / GitHub Actions)도 정하지 않았다. 지금 할 일이 아니다.

## 결정

**A를 채택한다.**

collector 안:
- 수집 실패 → 기록, **워터마크는 전진하지 않는다**(저장이 확인되지 않은 구간을 건너뛰지 않기 위해 — 기존 규칙 그대로).
  임베딩·매칭은 계속한다.
- 임베딩 실패 → 기록, 매칭은 계속한다(이미 임베딩된 논문과 관심사로).
- **예외: `EmbeddingDimensionError`는 즉시 중단한다.** 벡터 차원이 설정과 다르다는 건 데이터가 이미 깨졌다는
  신호라, 그 위에서 매칭을 돌리면 틀린 결과를 저장한다(기존 규칙 그대로).
- 매칭 실패 → 기록.
- 수집 교착 검사(상한 도달·워터마크 정체)는 기존처럼 맨 끝에, 다른 실패와 함께 모아 보고한다.
- 하나라도 실패했으면 모든 단계가 끝난 뒤 실패한 단계 이름과 원인을 담아 exit 1.

파이프라인(`pipeline:run`):
- collect · evaluate · brief를 **항상 셋 다** 돌린다. 각 단계는 DB에 있는 것으로 일한다.
- 하나라도 실패했으면 마지막에 exit 1. 어느 단계가 실패했는지 요약을 찍는다.

## 결과

- arXiv·Voyage 장애가 있는 날에도 어제까지 쌓인 후보로 판정·평가·브리핑이 돈다.
- exit 1이 "브리핑이 안 나갔다"를 뜻하지 않는다. 알람을 받으면 단계별 요약 로그를 본다.
- **이 결정으로 풀리지 않는 것**: Anthropic API 장애처럼 **판정·평가·요약 자체**가 의존하는 API가 죽으면
  여전히 그날 새 후보는 처리되지 않는다. PRD §5의 "전날 미배달 논문으로 채운다"는 briefer의 몫이다.
