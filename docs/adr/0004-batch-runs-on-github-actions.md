# 0004. 새벽 배치는 GitHub Actions에서 돈다

- 상태: 채택 (사용자 결정)
- 날짜: 2026-10-06
- 근거 기록: `HISTORY.md` 2026-10-05 「첫 전체 파이프라인 실행」 — 단계별 실측 시간

## 배경

CLAUDE.md는 배치 실행을 "Vercel Cron 또는 GitHub Actions"로 열어 두었다. 2026-10-05 첫 전체 실행의 실측은
collect 70.8초(arXiv 429로 수집 0편이었던 날) · evaluate 174.8초 · brief 81.4초였고, 2026-09-30 evaluate는
107편에 약 7.5분이 걸렸다. 수집이 3,000편 상한까지 받는 날은 arXiv 3초 간격만으로 15페이지 × 3초에 페이지당
응답 시간이 더해진다. **세 단계를 합치면 5분을 쉽게 넘는다.**

## 검토한 선택지

### A. Vercel Cron

Vercel Hobby 문서 기준(2026-10-05 확인): cron은 하루 1회, 실행 시각이 지정 시각에서 최대 ±59분 흔들리고,
함수 하나는 최대 300초다.

- 파이프라인을 한 함수로 못 돌린다. 단계마다 라우트를 나누고 이어 부르는 체인이 필요하다 — 그런데 하루 1회
  cron이라 단계별 cron을 따로 걸 수도 없다.
- evaluate 하나도 후보가 많은 날은 300초를 넘는다. 단계 안을 다시 쪼개 이어 받는 구조가 필요해진다.
- 웹과 같은 배포 단위라 파이프라인 의존성(Anthropic SDK·XML 파서)이 웹 번들 쪽 설정과 엮인다.

### B. GitHub Actions (채택)

- 잡 하나가 최대 6시간. `pnpm pipeline:run`(ADR 0003의 단계 격리 스크립트)을 로컬과 **똑같이** 돌린다.
  로컬 재현 = 배치 재현.
- `workflow_dispatch`로 손으로도 돌린다. 실패하면 GitHub가 알림 메일을 보낸다.
- 공개 저장소라 실행 시간이 무료다.

대가:
- **로그가 공개다.** 저장소가 public이라 Actions 로그를 누구나 본다. 로그에 사용자 이메일·관심사 이름·
  API 응답 원문 중 사용자를 드러내는 것을 찍지 않는다(이 결정과 함께 collector 관련성 판정 로그에서 관심사
  이름·응답 원문을 뺐다). 사용자 ID(UUID)와 논문 ID는 남긴다.
- GitHub cron은 정시 보장이 없다. 부하가 몰리면 수십 분 늦거나 드물게 건너뛴다 — 정각 대신 03:17 KST.
  브리핑은 "아침에" 있으면 되므로 감수한다.
- 공개 저장소의 schedule은 저장소 활동이 60일 없으면 자동으로 꺼진다.
- 러너 IP는 여러 사용자가 공유한다. arXiv 429가 로컬보다 잦을 수 있다(추측, 관측 전).
  429 재시도는 `Retry-After`를 따르고 없으면 30·60·120초로 기다리게 바꿨다(`packages/core/src/http.ts`).

## 결정

`.github/workflows/pipeline.yml` — 매일 18:17 UTC(03:17 KST)와 수동 실행. `pnpm db:migrate` 후
`pnpm pipeline:run`. 비밀값은 저장소 시크릿 `DATABASE_URL`(Neon) · `ANTHROPIC_API_KEY` · `VOYAGE_API_KEY` ·
`OPENALEX_MAILTO`.

마이그레이션을 배치에서 적용하는 이유: 파이프라인 코드가 기대하는 스키마와 DB가 어긋나면 그날 배치가 통째로
실패한다. drizzle 마이그레이션은 이미 적용된 것을 건너뛰므로 매일 돌려도 된다.

## 풀리지 않는 것

- 러너에서 arXiv 429가 얼마나 나는지 — 첫 며칠 실행 결과를 HISTORY.md에 남기고, 잦으면 실행 시각을 옮기거나
  수집만 따로 재시도하는 잡을 검토한다.
- 웹 배포(Vercel)가 마이그레이션보다 먼저 나가면 배치 전까지 웹이 새 스키마를 못 볼 수 있다. 배포 파이프라인을
  만들 때 다시 본다.
